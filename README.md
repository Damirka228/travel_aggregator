# Travel Aggregator

Высоконагруженный распределённый агрегатор комбо-туров (авиабилеты + отели) с гибким поиском «откуда угодно и куда угодно». Проект спроектирован по канонам Чистой Архитектуры (Clean Architecture), оптимизирован под Low-Latency выдачу в условиях жестких Rate Limit'ов внешних API и защищен ультимативным слоем автоматического тестирования.

## 🛠 Технологический стек & Инженерия

Приложение построено на базе современных, максимально эффективных инструментов Go-экосистемы, полностью исключающих оверхед на рефлексию:

*   **Language:** Go (Golang) — строгая типизация, высокая производительность, легковесные горутины.
*   **Routing & Web:** `go-chi/chi/v5` — высокоэффективный, идиоматичный роутер со стопроцентной совместимостью с `net/http`.
*   **Database & ORM:** PostgreSQL + `pgx/v5` + `sqlc` — компилируемое в Go-код генерирование SQL-запросов без runtime-затрат.
*   **Distributed Cache:** Redis — отказоустойчивое хранилище key-value для реализации общего кэша.
*   **Security & Crypto:** `golang-jwt/jwt/v5` для генерации сессионных токенов доступа + `bcrypt` для хэширования паролей.
*   **Observability:** Структурированный логгер `zerolog` с асинхронной ротацией файлов (`lumberjack`) + профайлер `net/http/pprof`.

## 📐 Архитектура проекта (Clean Architecture)

Кодовая база строго разнесена по независимым слоям. Направление зависимостей идет строго извне вовнутрь (внешние слои знают о внутренних, но не наоборот).

| Слой | Директория | Зона ответственности / Выполняемая задача |
| :--- | :--- | :--- |
| **App Initialization** | `cmd/app/` | Точка входа. Чтение конфигурации, поднятие пулов БД, сборка матрешки зависимостей (Dependency Injection). |
| **Delivery Layer** | `internal/delivery/http/` | Сетевые ворота. Прием HTTP-запросов, разбор параметров через `strconv`, валидация данных, отдача JSON. |
| **UseCase Layer** | `internal/usecase/` | Мозг системы. Оркестрация данных, запуск параллельных горутин через `errgroup`, скоринг и сборка комбо-туров. |
| **Repository Layer** | `internal/repository/` | Инфраструктура даты. Прямые SQL-запросы к Postgres, маппинг типов `sqlc`, сетевые клиенты к Travelpayouts API. |
| **Cache Layer** | `internal/cache/` | Декораторы защиты. Реализация двухслойной логики сохранения данных (L1 ОЗУ + L2 Redis). |
| **Domain Layer** | `internal/domain/` | Ядро бизнеса. Чистые структуры (`Flight`, `Hotel`), интерфейсы репозиториев и статический IATA-справочник. |

## ⚡ Механизм двухслойной защиты кэширования (Low-Latency)

Чтобы защитить сервер от падений при Rate Limit со стороны Авиасейлса, в проекте реализована гибридная стратегия кэширования:

Пользовательский запрос ➡️ [HTTP Handler]
│
▼
🔎 Проверка в L1 (In-Memory) ──➡️ [HIT: ~0.1 ms] ➡️ Отдать юзеру
│
[MISS]│
▼
🔎 Проверка в L2 (Redis)     ──➡️ [HIT: ~1.5 ms] ➡️ Загреть L1 ➡️ Отдать
│
[MISS]│
▼
🌐 Запрос во внешнее API     ──➡️ [HTTP: ~6.0 s]  ➡️ Загреть L1 + L2 ➡️ Отдать

1. **L1 (In-Memory Shared Cache):** Потокобезопасная мапа с мьютексами (`sync.RWMutex`) внутри памяти Go-процесса. Скорость отдачи — наносекунды.
2. **L2 (Distributed Redis Cache):** Общий кэш в Docker-контейнере. Спасает приложение при перезапуске Go-сервера (когда ОЗУ очищается).

## 🛡 Надежность кодовой базы (Code Coverage Summary)

Критически важная бизнес-логика и сквозные сценарии полностью покрыты Unit и интеграционными HTTP-тестами (`net/http/httptest`). Написанный руками код имеет беспрецедентный уровень защиты:

*   **`internal/usecase/`** — **80.5%** (Полное тестирование сценариев сортировки, фильтрации бюджетов и скоринга).
*   **`internal/cache/`** — **86.5%** (Тестирование логики переключения слоев кэша при промахах и попаданиях).
*   **`internal/delivery/http/`** — **72.5%** (Интеграционные тесты ручек авторизации `/auth/signup`, `/auth/signin` и `/destinations`).
*   **`internal/infrastructure/auth/`** — **91.7%** (Тестирование криптографического хэширования bcrypt и jwt-генерации).
*   **`internal/domain/`** — **100.0%** (Полное покрытие статического IATA-справочника перевода городов мира).

## 🎯 Продуктовые номинации выдачи (Комбо-Туры)

UseCase слой не просто отдает сухой массив билетов, а автоматически скрещивает в памяти перелеты туда-обратно с ценой проживания в отелях конкретного города прилета, рассчитывая общую стоимость за **весь указанный период (`days`)**:

*   **`best_tour`** — 1 рекомендуемый вариант-чемпион. Рассчитывается по весовой формуле баланса: `ПолнаяЦена - (ЗвездностьОтеля * 2000)`. Поощряет комфортные отели, если они стоят адекватных денег.
*   **`cheapest_tours`** — Сортировка Топ-5 туров строго по росту итоговой стоимости (идеально для ультра-эконом путешествий).
*   **`longest_tours`** (Luxury-туры) — Топ-5 предложений, отсортированных по максимальному комфорту и звездности гостиниц, проходящих по бюджету пользователя.

## 🚀 Инструкция по быстрому запуску

### 1. Подготовка окружения
Склонируйте репозиторий и создайте в корне файл `.env`:
```env
PORT=8080
DATABASE_URL=postgres://postgres:postgres@localhost:5432/travel_db?sslmode=disable
REDIS_URL=localhost:6379
JWT_SECRET=your_super_secret_highload_key
TRAVELPAYOUTS_TOKEN=your_aviasales_api_token
```

### 2. Поднятие Docker-инфраструктуры
Запустите контейнеры базы данных PostgreSQL и кэша Redis:
```bash
docker-compose up -d
```

### 3. Сборка и старт приложения
Запустите компиляцию проекта и старт веб-сервера через Makefile:
```bash
make run
```

### 4. Тестирование сквозного поиска
Отправьте проверочный запрос через `curl`, прогнав сырой текст через красивый парсер `jq`:
```bash
curl -s "http://localhost:8080/destinations?budget=300000&days=7&city=MOW" | jq
```
