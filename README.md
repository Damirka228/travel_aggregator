# Travel Aggregator

Backend-сервис на Go для подбора комбинаций авиабилетов и проживания в пределах бюджета. Пользователь указывает город вылета, дату начала поездки, количество дней и бюджет. API возвращает рекомендуемый вариант, самые дешёвые туры и варианты с наиболее высокой категорией отеля.

Проект демонстрирует работу с внешним API, PostgreSQL, двухуровневым кэшем и параллельным получением данных. Каталог отелей пока содержит демонстрационные предложения; бронирование и проверка наличия номеров не реализованы.

## Возможности

| Возможность | Реализация |
| --- | --- |
| Поиск туров | Подбор перелёта туда-обратно на заданные даты и проживания; фильтрация по бюджету и точной длительности |
| Источники билетов | Travelpayouts API и таблица `destinations` в PostgreSQL |
| Параллельное получение данных | Запросы к PostgreSQL и репозиторию внешнего API выполняются через `errgroup`; таймаут каждого источника — 10 секунд |
| Одновременные запросы | `singleflight` объединяет загрузки из внешнего API с одинаковым городом вылета и датами |
| Валидация | Обязательная дата в формате `YYYY-MM-DD`, положительное целое число дней, конечный бюджет больше 1000 ₽ |
| Сбои источников | Работа с доступным источником при частичном отказе; HTTP 503 при отказе всех источников |
| Кэш билетов | L1 в памяти процесса: 5 минут; L2 в Redis: 1 час; удаление просроченных записей L1 при чтении и раз в минуту |
| Регистрация и вход | Хэширование паролей через bcrypt, выдача JWT на 24 часа |
| HTTP-маршрутизация | Отдельный `Router` с `NewRouter` и `SetupRoutes`; middleware для request ID, логирования и восстановления после panic в HTTP-обработчике |
| Завершение работы | Обработка SIGINT/SIGTERM, остановка фоновой очистки и общих загрузок, ожидание запросов и закрытие ресурсов |
| Диагностика | Структурированные логи, ротация файлов, опциональный pprof |

## Архитектура

Код разделён на слои. Обработчики принимают HTTP-запросы, use case собирает и ранжирует предложения, а репозитории обращаются к источникам данных. Интерфейсы репозиториев объявлены в `domain`; зависимости собираются в `cmd/app`.

| Директория | Назначение |
| --- | --- |
| `cmd/app/` | Конфигурация, сборка зависимостей, запуск и остановка приложения |
| `internal/domain/` | Модели, интерфейсы репозиториев, справочник IATA |
| `internal/usecase/` | Поиск и ранжирование туров, регистрация и вход |
| `internal/delivery/http/` | Роутер, разбор HTTP-запросов и формирование ответов |
| `internal/repository/` | Адаптеры PostgreSQL, Redis, Travelpayouts и каталог отелей |
| `internal/cache/` | Кэш в памяти и декоратор репозитория билетов |
| `internal/infrastructure/` | Логирование, хэширование паролей и создание JWT |
| `queries/` | SQL-запросы для генерации кода через sqlc |
| `migrations/` | Миграции схемы PostgreSQL |

### Получение билетов

Use case передаёт источникам `FlightSearch`: город отправления, дату вылета и дату обратного вылета. Источники запрашиваются параллельно, затем их результаты объединяются.

| Источник | Поведение |
| --- | --- |
| PostgreSQL | SQL фильтрует записи по `origin`, `departure_date` и `return_date`; длительность рассчитывается из дат |
| Travelpayouts | Используется `/aviasales/v3/prices_for_dates` с обеими датами, `one_way=false` и валютой RUB; ответ переводится в модель `Destination` |
| Частичный отказ | Ошибка источника логируется; предложения доступного источника продолжают участвовать в подборе |
| Все источники недоступны | Возвращается HTTP 503 |
| Успешный источник без предложений | Считается доступным; итоговый ответ может быть пустым с HTTP 200 |

Адаптер Travelpayouts сохраняет время обоих вылетов и пропускает предложения с некорректными датами, другим городом отправления, несовпадающими календарными датами или неположительной ценой. Метод возвращает найденные ранее цены из кэша Aviasales. Подробнее об источнике данных и параметрах — в [документации Travelpayouts](https://support.travelpayouts.com/hc/en-us/articles/203956163-Aviasales-Data-API).

### Кэширование и общие загрузки

Кэш используется для репозитория Travelpayouts. PostgreSQL запрашивается отдельно при каждом поиске.

```text
L1: память процесса → L2: Redis → Travelpayouts API
```

| Событие | Действие |
| --- | --- |
| Попадание в L1 | Данные возвращаются из памяти |
| Промах L1, попадание в L2 | Данные возвращаются из Redis и сохраняются в L1 |
| Промах обоих уровней | Выполняется запрос в API; результат сохраняется в L1 и L2 |
| Ошибка Redis после запуска приложения | Поиск продолжается через L1 или API; ошибка записи в L2 не отменяет полученный результат |
| Ключ отсутствует в Redis | Обычный промах кэша; `redis.Nil` не логируется как ошибка |

Формат ключа:

```text
destinations:<origin>:<departure_date>:<return_date>
destinations:MOW:2026-11-10:2026-11-17
```

Бюджет не входит в ключ: кэш хранит билеты на выбранные даты, а фильтрация по бюджету и подбор отелей выполняются в use case для каждого запроса.

При промахе кэша `singleflight.DoChan` объединяет одновременные загрузки с одним ключом. Разные города или даты загружаются независимо. Объединение действует внутри одного процесса и только пока загрузка выполняется.

Отмена пользовательского запроса прекращает ожидание этого пользователя. Общая загрузка использует контекст приложения с таймаутом 10 секунд; остальные ожидающие пользователи могут получить её результат. При остановке приложения загрузки отменяются и ожидается их завершение.

L1 разделён на 256 шардов с отдельными блокировками. Просроченные записи удаляются при чтении и фоновой очисткой раз в минуту; тикер останавливается вместе с приложением.

## Локальный запуск

Понадобятся Go 1.26.6, Docker с Compose и установленный Goose CLI (`goose`). `sqlc` требуется только при изменении SQL-запросов или схемы и последующей генерации кода.

### 1. Получить проект и подготовить конфигурацию

```bash
git clone https://github.com/Damirka228/travel_aggregator.git
cd travel_aggregator
cp .env.example .env
```

В `.env` задайте `JWT_SECRET` и `TRAVELPAYOUTS_TOKEN`. Для секрета JWT можно использовать случайное значение, например сгенерированное командой `openssl rand -hex 32`.

| Переменная | Значение по умолчанию / пример | Назначение |
| --- | --- | --- |
| `PORT` | `8080` | Порт HTTP-сервера |
| `DATABASE_URL` | `postgres://travel:travel@localhost:5432/travel_aggregator?sslmode=disable` | Подключение к PostgreSQL; обязательная настройка |
| `REDIS_ADDR` | `localhost:6379` | Адрес Redis в формате `host:port` |
| `JWT_SECRET` | Задаётся пользователем | Обязательный секрет подписи JWT |
| `TRAVELPAYOUTS_TOKEN` | Задаётся пользователем | Обязательный токен Travelpayouts API |
| `ENABLE_PPROF` | `false` | Включает маршруты профайлера под `/debug` |

Для совместимости поддерживаются прежние имена `POSTGRESQL_STR` и `REDIS_URL`. Если указаны оба варианта, приоритет имеют `DATABASE_URL` и `REDIS_ADDR`. `REDIS_URL` также должен содержать адрес `host:port`, а не URL с протоколом.

Переменные окружения процесса имеют приоритет над `.env`. При запуске проверяются обязательные настройки и доступность PostgreSQL и Redis; на подключение выделяется до 10 секунд.

### 2. Запустить PostgreSQL и Redis

```bash
docker compose up -d
```

### 3. Применить миграции

После готовности PostgreSQL выполните:

```bash
make migrate-up
```

По умолчанию Makefile использует те же параметры базы, что и Docker Compose. Для другой базы передайте строку подключения явно:

```bash
make migrate-up DB_URL='postgres://user:password@host:5432/database?sslmode=disable'
```

Приложение не применяет миграции автоматически.

### 4. Собрать и запустить сервер

```bash
make build
./bin/app
```

Для разработки также доступна команда `make run`. При работе с процессом напрямую используйте собранный бинарный файл: SIGINT/SIGTERM должны поступать самому приложению.

## HTTP API

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/destinations` | Подобрать туры |
| `POST` | `/auth/signup` | Зарегистрировать пользователя и получить JWT |
| `POST` | `/auth/signin` | Войти и получить JWT |
| `GET` | `/debug/pprof/` | Профайлер; доступен только при `ENABLE_PPROF=true` |

Поиск сейчас доступен без JWT. Регистрация и вход выдают токены, но middleware для проверки токенов и защищённые пользовательские маршруты пока не реализованы. Профайлер предназначен для разработки; при включении его маршруты не требуют авторизации.

### Поиск туров

```bash
curl -i --get 'http://localhost:8080/destinations' \
  --data-urlencode 'city=MOW' \
  --data-urlencode 'budget=150000' \
  --data-urlencode 'departure_date=2026-11-10' \
  --data-urlencode 'days=7'
```

| Параметр | Пример | Использование |
| --- | --- | --- |
| `budget` | `150000` | Максимальная суммарная стоимость в рублях; конечное число больше 1000; `NaN` и бесконечности отклоняются |
| `days` | `7` | Положительное целое число: точная разница календарных дат вылета туда и обратно |
| `city` | `MOW` | Обязательный IATA-код города вылета |
| `departure_date` | `2026-11-10` | Обязательная календарная дата начала поездки в формате `YYYY-MM-DD` |

Дата обратного вылета рассчитывается через `departure_date.AddDate(0, 0, days)`. Для `2026-11-10` и `days=7` это `2026-11-17`. Более короткие и длинные поездки исключаются. Для живого поиска замените дату примера на дату нужной поездки.

Ответ содержит следующие поля:

| Поле | Содержимое |
| --- | --- |
| `best_tour` | Один тур с минимальным значением скоринга |
| `cheapest_tours` | До пяти туров по возрастанию суммарной стоимости |
| `longest_tours` | До пяти туров по убыванию звёздности отеля; историческое имя поля |

Каждый тур содержит `flight`, `hotel`, `total_price` и `description`. В `flight` возвращаются `Origin`, `City`, `Price`, `Days`, `DepartureAt` и `ReturnAt`; времена вылетов сериализуются в RFC 3339. Для предложений внешнего API поле `Country` остаётся пустым.

### Расчёт стоимости и ранжирование

```text
total_price = flight.Price + hotel.Price × days
score = total_price − hotel.Stars × 2000
```

`flight.Price` учитывается один раз как стоимость предложения туда-обратно. `hotel.Price` — демонстрационная цена одной ночи. В текущей модели `days` принимается равным количеству ночей: предполагается прибытие в день вылета и выезд в день обратного рейса. Время прибытия, правила заселения и наличие номеров не учитываются.

Например, перелёт за 8762 ₽ и проживание по 1200 ₽ при `days=7` дают `8762 + 1200 × 7 = 17162 ₽`. Тур с суммарной стоимостью, равной бюджету, допускается; превышающий бюджет — исключается.

Рекомендуемый тур имеет минимальный `score`. Коэффициент 2000 задаёт вес звёздности отеля в этом правиле; это эвристика ранжирования. `longest_tours` сохраняет историческое имя и означает подбор по звёздности, а не по длительности. Все отобранные туры соответствуют одному запрошенному количеству дней.

### Статусы поиска

| Статус | Условие |
| --- | --- |
| `200` | Поиск завершён; при отсутствии подходящих туров поля `best_tour`, `cheapest_tours` и `longest_tours` равны `null` |
| `400` | Отсутствующие или некорректные параметры: бюджет, дни, город или дата |
| `503` | Все настроенные источники билетов вернули ошибки |
| `500` | Другие ошибки use case |

Ошибки поиска возвращаются текстом. Например:

```bash
curl -i 'http://localhost:8080/destinations?city=MOW&budget=NaN&departure_date=2026-11-10&days=7'
```

```text
HTTP 400
invalid budget: expected a finite number greater than 1000
```

```bash
curl -X POST 'http://localhost:8080/auth/signup' \
```

## Завершение работы

SIGINT или SIGTERM отменяет корневой контекст приложения. Фоновая очистка L1 останавливается, а общие загрузки получают отмену.

`App.Shutdown` прекращает приём новых соединений и ожидает активные HTTP-запросы с дедлайном 15 секунд. При истечении дедлайна HTTP-соединения закрываются принудительно. Затем `CachedDestinationRepository.Close` запрещает новые загрузки, отменяет текущие и ожидает их завершения через `WaitGroup`. После этого закрываются пул PostgreSQL, клиент Redis и файл логов.

Дедлайн 15 секунд ограничивает HTTP shutdown; ожидание загрузок в `Close` не имеет отдельного дедлайна и требует соблюдения контекста зависимостями. Повторный сигнал во время остановки возвращает стандартное поведение ОС.

Очистка ресурсов выполняется также при ошибке запуска. Повторный вызов `App.Shutdown` безопасен.

### Интеграционный тест PostgreSQL

Запустите PostgreSQL и примените миграции. Затем укажите строку подключения:

```bash
TRAVEL_TEST_DATABASE_URL='postgres://travel:travel@localhost:5432/travel_aggregator?sslmode=disable' \
  go test -race -tags=integration -count=1 -timeout=90s ./internal/repository/postgres
```

Тест использует реальный драйвер и SQL-запрос. На отдельном соединении создаётся временная таблица с копией схемы `public.destinations`; фикстуры записываются только в неё. Проверяются фильтры по городу и обеим датам, расчёт длительности, сортировка, исключение неполных записей и ограничение порядка дат.

Без тега `integration` тест не включается в сборку. Если тег указан, но `TRAVEL_TEST_DATABASE_URL` отсутствует, тест пропускается.

### Проверка кэша вручную

1. Выполните запрос `/destinations` с выбранными датами. При промахах обоих уровней в логах появится обращение к Travelpayouts.
2. Повторите тот же запрос до истечения TTL L1: ожидается `Попадание в L1 кэш (ОЗУ)`.
3. Перезапустите приложение и повторите запрос до истечения TTL Redis: ожидается `Промах L1. Попадание в L2 кэш (Redis)`.

Если данные уже были в Redis, первый запрос может сразу попасть в L2. Для проверки другого ключа измените дату поездки.

### Бенчмарк

Для измерения бизнес-логики на 100 демонстрационных билетах:

```bash
go test ./internal/usecase -run '^$' -bench BenchmarkFindDestinations -benchmem
```

Этот бенчмарк не измеряет задержки внешнего API, базы или Redis. Результаты зависят от оборудования и условий запуска; показатели RPS и SLA в проекте не заявляются.

## Текущие ограничения

| Область | Ограничение |
| --- | --- |
| Отели | Статический демонстрационный каталог; для неизвестного города возвращается шаблонное предложение; актуальность цен и наличие номеров не проверяются |
| Данные API | Цены из кэша Aviasales; адаптер получает первую страницу до 100 предложений, без дальнейшей пагинации |
| Проживание | Число ночей принимается равным `days`; время прибытия и правила заселения не учитываются |
| Записи PostgreSQL | Записи без города отправления, нужных дат или времени рейсов не участвуют в подборе; старые строки требуют заполнения новых полей |
| Параметры | Проверка даты не запрещает прошлые даты; формат и существование IATA-кода не проверяются; отдельного верхнего предела `days` нет |
| Кэш | L1 не имеет лимита количества записей; `singleflight` объединяет загрузки только внутри одного процесса |
| Бронирование | Покупка билетов, бронирование отелей и оплата отсутствуют; стоимость в ответе — оценка перелёта и проживания |
